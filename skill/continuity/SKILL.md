# continuity：让下一个 Agent 接得上

两份文件，一个原则：

- `SPEC.md`：要造什么，很少变。模板：`templates/SPEC.md`
- `STATE.md`：做到哪了，经常变，≤ 80 行。模板：`templates/STATE.md`
- **代码、git、测试 > STATE > 聊天记录。** 冲突时以前者为准，并修正 STATE。

用户不需要懂这些。不要对用户讲 Spec、SDD 这类术语，用大白话说"我把需求和进度记在项目里，换谁来都能接着做"。

下面有三个动作。先判断当前属于哪一个。

---

## init：建立 SPEC + STATE

**什么时候用：** 项目里没有 SPEC.md 或 STATE.md。

1. 先看项目里已有的东西（README、文档、代码结构、package.json 等），能推断的就不问。项目还不是 git 仓库时，先 `git init`（接力靠 git 记录进度）。
2. 和用户正常聊需求。**只问会改变方案的问题，最多 5 个**，一次问完，尽量给选项。
3. 按模板写 `SPEC.md`：
   - 只写外部看得到的行为，不写类名、函数名、实现步骤。
   - 每条关键需求都附"怎样算做到"。
   - 有界面的项目，写全空数据、加载中、出错、没权限等状态。
   - 没用的章节直接删。
4. 按模板写 `STATE.md`：
   - 把工作拆成 3～10 项任务清单，写上「下一步」。
   - 写「验证方式」：优先用项目已有的一条命令（`npm test`、`make test`、构建命令），并写明通过时应看到什么；还没有测试的，写可操作的检查方法（如"打开首页能看到 X"）。目标要能直接检查，不用问人。
   - 聊需求时没定下来的事，写进「待确认问题」。
5. 项目根目录没有 `AGENTS.md` 接力规则时（找 `cross-agent-dev:start` 标记），把本 Skill 目录下 `AGENTS.block.md` 的全部内容追加到项目根目录的 `AGENTS.md`（没有就新建）；再确认 `CLAUDE.md` 里有一行 `@AGENTS.md`（没有就加上）。
6. 装提交检查：`bash <本 Skill 目录>/hooks/install-hook.sh`。它会在连续多次提交代码却没更新 STATE 时拦下提交；可重复运行，不会覆盖项目已有的检查。
7. 把 SPEC.md、STATE.md、AGENTS.md、CLAUDE.md 提交到 git。
8. 用 3 行告诉用户：记下了什么、第一步做什么。

已有项目第一次接入时：用 git log 和代码把已经做完的部分写成 `[x]`（能验证的先验证），不要重做。

---

## checkpoint：手动存档

**什么时候用：** 用户说要换 Agent、额度快没了、先存个档，或者你觉得刚完成了一段重要工作。

1. 看 `git status`、`git diff`、最近的 `git log`，对照 STATE 的任务清单。
2. 更新 STATE：
   - 先跑「验证方式」。只勾掉验证通过的项；没法验证的写"（未验证）"。
   - 做了一半的标 `[~]`，写清**做到哪、差什么、在哪个文件**。这是下个 Agent 最需要的信息。
   - 卡住做不下去的标 `[!] 受阻`，写清原因和需要谁做什么（比如"等用户提供 API Key"）。不要让卡住的任务一直挂在 `[~]`。
   - 这次对话里做出的决定写进「有效决定」，附原因。新决定推翻了旧决定，就改写旧的那条，不要让"用 A"和"改用 B"并存。聊天中试过又放弃的方案，只有对将来还有用时才写一句"不用 X，因为…"。
   - 还没定、需要用户拍板的事写进「待确认问题」；用户已经定了的，移到「有效决定」。
   - 写清「下一步」，要具体到下个 Agent 看完就能动手。
   - 更新顶部的时间和你的名字（Claude Code / Codex / …）。
3. 超过 80 行就压缩：已完成的项合并成一行；长期有效的产品约束搬进 SPEC 的「约束」，反复踩的开发坑搬进 AGENTS.md 规则块之外的地方，再删。
4. **自检：** 假装你是一个没看过这段聊天的新 Agent，只读 SPEC + STATE，能不能直接接着做？哪里需要猜，就补哪里。
5. `git add` 相关文件后 commit（信息如 `chore: checkpoint STATE`）。有没写完的代码时，一并提交并在 commit 信息里注明 WIP，这样换 Agent 时不会丢。
6. 告诉用户：存好了，换过去后说一句"继续这个项目"即可。

**不要写进 STATE：** 聊天原文、推理过程、代码片段、git 已经能查到的东西（改了哪些文件、commit 列表）。

---

## recover：从上个 Agent 的对话记录补全

**什么时候用：** 开工对账时发现 STATE 明显落后，比如有大量没记录的未提交改动、STATE 时间之后还有 commit、`[~]` 项没写清做到哪；或者 SPEC / STATE 根本不存在，但项目已经做了一部分。

1. 列出候选对话：

   ```bash
   python3 <本 Skill 目录>/scripts/recover.py --list
   ```

   标着"可能是当前对话"的是你自己，跳过。只有一个明显候选时直接用；多个候选时让用户选。

2. 读取摘录（已自动脱敏、压缩）：

   ```bash
   python3 <本 Skill 目录>/scripts/recover.py --session <编号>
   ```

   对话太长、摘录被截断太多时，加 `--filter keyword`，只保留像是决定、进度、问题的消息，再加上结尾部分。
   摘录里每条消息都有编号 `#N`。想看被跳过的某段完整内容，用 `--session <编号> --from <N>` 从那里逐页往下读。

   **某个决定不在最近这次对话里**（比如 STATE 提到"用 X"，但原因找不到）：在本项目所有历史对话里搜关键词，再按结果里给的命令去读上下文：

   ```bash
   python3 <本 Skill 目录>/scripts/recover.py --search "关键词"
   ```

3. 从摘录里**只提炼**：最终决定和原因、每项任务的进度、做了一半的事、踩过的坑、原本打算的下一步。前后矛盾时以时间靠后的为准。

4. **逐条和代码、git、测试核对**。聊天里说"做完了"的，要在代码里确认；核对不上的写成"聊天里说做了 X，代码里没找到"。

5. 按 checkpoint 的规则写进 STATE。**不要把对话原文抄进 STATE**，STATE 会进 git。

6. 告诉用户：从哪个对话补了什么，有什么核对不上。

**失败时：** 脚本报"格式没读懂"、没权限读 `~/.claude` 或 `~/.codex`、找不到记录，就如实告诉用户，改用 STATE + git + 代码恢复。不要猜。

---

## 开工对账（每次接手都做，也是 AGENTS.md 规则 1～4）

1. 读 SPEC、STATE → `git status` / `git diff --stat` / `git log -5 --oneline`。
2. 跑 STATE「验证方式」里的命令，确认 `[x]` 的项确实成立。
3. 发现不一致：以代码为准修正 STATE；STATE 明显落后就走 recover。
4. 项目还没装提交检查时（`.git/hooks/pre-commit` 里没有 `cross-agent-dev:state-check`），运行 `bash <本 Skill 目录>/hooks/install-hook.sh` 补上。
5. 动手前用 3～5 行告诉用户："上个 Agent 做到第 X 项；第 Y 项做了一半，差 Z；第 W 项受阻，需要你做 V；有 N 个待确认问题；我从这里继续。"用户确认后再开始。
